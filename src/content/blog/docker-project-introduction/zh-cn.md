很多人第一次接触 Docker 时，会把它理解成“另一种虚拟机”。这个说法不算完全错误，但并不准确。

更容易理解的方式是：Docker 把项目代码、运行环境、依赖和启动方式封装在一起，让项目可以在不同机器上以相对一致的方式运行。对一个需要长期部署的项目来说，这种一致性往往比“在服务器上手动装好一切”更重要。

## Docker 到底解决了什么问题

一个项目通常不只有源代码，还依赖特定版本的 Python 或 Node.js、第三方库、系统工具、环境变量，以及一套固定的启动顺序。

如果这些内容都直接安装在服务器上，时间一长就容易出现各种问题：

- 本地能运行，服务器不能运行；
- 升级某个依赖后，另一个服务突然出错；
- 换了一台服务器，需要重新手动配置一遍；
- 项目之间互相污染，难以判断问题来自哪里。

Docker 的思路是把这些运行条件一起描述出来，构建成可以重复启动的环境。这样，部署的重点就从“在服务器上重新搭环境”，变成“准备好镜像并启动容器”。

## 新手应该先认识哪些东西

Docker 的基本使用可以拆成几步：准备镜像、启动容器、查看运行状态、读取日志，最后在需要时停止或删除容器。

除了镜像和容器，还经常会遇到下面几个概念：

- Docker Engine：真正负责构建镜像和运行容器的后台服务；
- Docker CLI：我们在终端中输入的 `docker` 命令；
- 镜像仓库：保存和分发镜像的地方，可以使用公共仓库，也可以使用私有仓库；
- Dockerfile：描述如何构建镜像的文本文件；
- 数据卷：让数据脱离容器生命周期，适合保存数据库和上传文件；
- 网络：让多个容器通过服务名互相访问，而不必把所有端口暴露给外部。

在 Windows、macOS 或 Linux 上安装 Docker 后，可以先用下面的命令确认 Docker 是否正常工作：

```bash
docker --version
docker run hello-world
```

前一个命令用于查看客户端版本，后一个命令会拉取一个很小的测试镜像并启动容器。如果测试成功，说明 Docker 服务和本地命令行基本可用。

## 从镜像启动第一个容器

最常见的操作是从镜像启动容器：

```bash
docker run -d --name demo-web -p 8080:80 nginx
```

这条命令可以这样理解：

- `-d` 让容器在后台运行；
- `--name` 给容器起一个便于识别的名字；
- `-p 8080:80` 把宿主机的 8080 端口映射到容器的 80 端口；
- 最后的 `nginx` 是要使用的镜像名称。

启动后，可以用浏览器访问 `http://localhost:8080`。这里的端口映射很重要：容器内部的服务默认只能被容器网络访问，映射端口后，宿主机或外部用户才能按照指定端口访问它。

查看正在运行的容器：

```bash
docker ps
```

查看全部容器，包括已经停止的容器：

```bash
docker ps -a
```

停止和启动已有容器：

```bash
docker stop demo-web
docker start demo-web
```

如果确定不再需要这个容器，可以删除它：

```bash
docker rm demo-web
```

删除容器不会自动删除镜像。镜像和容器是两种不同的资源，清理时要分别确认。

## 镜像从哪里来

镜像通常有三种来源：从公共镜像仓库下载、从自己的 Dockerfile 构建，或者从私有镜像仓库拉取。

查看本地已有镜像：

```bash
docker image ls
```

手动拉取镜像：

```bash
docker pull nginx:latest
```

镜像名称后面的标签用于区分版本。学习和测试时可以使用明确的版本标签；生产环境不建议长期依赖容易变化的 `latest`，而应该固定一个经过验证的版本，以免同一条启动命令在不同时间得到不同结果。

## Dockerfile 是怎么工作的

如果项目不是直接使用现成镜像，就需要通过 Dockerfile 构建自己的镜像。一个简化的 Dockerfile 通常包含这些信息：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

它表达的是：以一个基础镜像开始，设置工作目录，安装依赖，复制项目文件，最后指定容器启动时执行的命令。

构建镜像：

```bash
docker build -t demo-app:1.0 .
```

这里的 `.` 表示构建上下文，也就是 Docker 可以读取的当前目录。实际项目中通常还需要通过 `.dockerignore` 排除缓存、日志、虚拟环境和本地密钥，避免把无关文件复制进镜像。

镜像构建完成后，就可以像使用其他镜像一样启动它：

```bash
docker run -d --name demo-app demo-app:1.0
```

## 容器、端口和环境变量

容器内部的端口和宿主机端口不是同一个概念。下面的写法表示“宿主机端口映射到容器端口”：

```text
宿主机端口:容器端口
```

同一个宿主机端口不能同时被多个服务占用。如果访问不到服务，可以检查三个地方：应用是否监听了正确端口、容器端口是否映射正确、宿主机防火墙是否允许访问。

配置通常不应该直接写死在镜像里，而是通过环境变量传入：

```bash
docker run -d \
  --name demo-app \
  -e APP_ENV=production \
  -e API_URL=https://example.invalid \
  demo-app:1.0
```

真实密码、令牌和私钥不要直接写进 Dockerfile，也不要提交到代码仓库。开发环境可以使用本地环境变量或未纳入版本控制的配置文件，生产环境则应使用更安全的密钥管理方式。

## 数据卷：让数据不跟着容器消失

如果容器需要保存文件，可以使用命名卷：

```bash
docker volume create demo-data
docker run -d --name demo-db -v demo-data:/var/lib/app demo-db:1.0
```

冒号左边是卷名，右边是容器内的目录。也可以把宿主机目录挂载到容器中，但要注意路径、权限和备份策略。

数据卷解决的是“数据保存在哪里”的问题，不等于自动完成备份。重要数据仍然需要定期备份，并且最好验证备份是否真的能够恢复。

## 如何查看容器内部发生了什么

查看日志：

```bash
docker logs demo-app
docker logs -f demo-app
```

进入正在运行的容器进行临时检查：

```bash
docker exec -it demo-app sh
```

查看容器的详细信息，例如端口、环境变量和挂载：

```bash
docker inspect demo-app
```

`docker exec` 适合排查问题，但不建议把它当成长期修改容器的方式。手动修改容器里的文件，容器重建后通常会丢失；需要永久生效的改动，应当回到代码或 Dockerfile 中修改，再重新构建镜像。

## 为什么经常使用 Docker Compose

当项目只有一个容器时，`docker run` 已经够用。项目包含前端、后端、数据库等多个服务后，逐个输入命令就容易遗漏参数，这时可以使用 Docker Compose。

Compose 用一个配置文件描述服务、网络、端口、环境变量和数据卷，然后通过统一命令管理整组服务：

```bash
docker compose up -d
docker compose ps
docker compose logs -f <service>
docker compose stop
```

Compose 的优势是启动方式更容易复现，也方便团队成员共享开发环境。不过，配置文件仍然可能引用敏感变量，提交或分享前要确认密钥没有被写进去。

## 新手容易遇到的几个误区

- 把容器当成永久服务器：容器应该可以随时重建，重要数据需要放在卷或宿主机目录中；
- 只看 `docker ps`：容器运行不代表应用健康，还要看日志和健康检查；
- 修改运行中的容器：临时修改不会自动变成新的镜像，正式修改应该回到 Dockerfile 或代码；
- 随意暴露端口：只有确实需要从外部访问的服务才应该映射到宿主机；
- 使用浮动版本：生产环境固定镜像版本，更容易排查和回滚；
- 把密钥打进镜像：镜像可能被缓存、复制和上传，敏感信息不应写入其中。

## 镜像和容器有什么区别

可以把镜像理解成一个只读的模板，里面包含应用代码、依赖和运行环境。

容器则是镜像启动后的运行实例。一个镜像可以启动多个容器，同一个容器也可以被停止、重启或删除。

简单地说：

- 镜像是模板；
- 容器是实例；
- Docker Compose 用来描述多个容器如何一起运行。

容器本身并不适合保存所有重要数据。容器可以被重建，甚至可以被删除，因此数据库、上传文件、日志归档等需要长期保留的内容，应当放在容器之外，再通过数据卷或目录映射提供给容器使用。

## 一个常见的前后端结构

以一个需要浏览器访问的项目为例，整体结构通常可以简化为：

```text
浏览器
  ↓ HTTP / HTTPS
前端容器：Web 服务器 + 前端页面
  ↓ Docker 内部网络
后端容器：API 服务 + 业务循环 + 外部服务适配器
  ↓
宿主机上的持久化数据目录
```

前端容器主要负责提供页面和转发请求，后端容器负责接口、业务逻辑以及与外部服务的通信。两个容器通过 Docker 内部网络连接，外部用户通常只需要访问前端暴露出来的端口。

这样的拆分有几个好处：前后端可以分别更新，问题更容易定位，也可以根据需要单独重启某一个服务。

## 数据为什么要放在容器外面

假设重要数据直接写在容器文件系统里，那么容器重建时，这些数据就可能一起消失。正确的做法通常是把宿主机上的持久化目录映射到容器内部：

```text
宿主机持久化目录  →  容器内数据目录
```

容器看到的只是容器内的路径，但真正的数据保存在宿主机上。因此，即使容器被删除并重新创建，只要映射关系没有改变，数据仍然可以继续使用。

这也是部署前必须确认的事项：如果程序启动时没有挂载到正确的数据目录，它可能会误认为自己面对的是一个全新的空数据库。对于涉及交易、订单或账户状态的系统，这种错误尤其危险。

还需要区分两类状态：

- 平台自己的数据库、日志和缓存，可以通过持久化目录保存；
- 外部交易平台上的真实仓位，属于外部账户状态，不会因为 Docker 容器被删除而消失。

## 常用的容器操作

查看服务状态：

```bash
docker compose ps
```

查看某个服务最近的日志：

```bash
docker compose logs --tail=200 <service>
```

持续追踪日志：

```bash
docker compose logs -f --tail=200 <service>
```

只重启一个服务：

```bash
docker compose restart <service>
```

这个操作适合临时恢复服务。它通常不会删除持久化数据，但会中断当前进程中的内存状态，因此不能把“重启”理解成完全没有影响。

重新构建镜像并启动服务：

```bash
docker compose up -d --build
```

这个命令适合开发环境或明确需要重新构建镜像的场景。正式环境更新时，最好使用经过备份、检查和回滚设计的部署流程，而不是直接在服务器上临时操作。

停止并删除容器：

```bash
docker compose down
```

它会停止并删除由 Compose 管理的容器，通常不会删除单独挂载在宿主机上的数据目录。之后可以再次启动服务，但仍然应该先确认数据映射和配置是否正确。

查看镜像、容器和磁盘占用：

```bash
docker image ls
docker ps -a
docker system df
```

清理 Docker 空间时要谨慎。类似 `docker system prune` 的命令可能删除暂时不用的镜像和缓存，导致回滚变得困难。正式环境中，清理之前应先确认当前版本、历史镜像和备份是否仍然可用。

## 正式更新不只是一次 git pull

对于需要稳定运行的服务，正式更新最好有一条明确的链路：

```text
本地修改并测试
    ↓
提交并推送代码
    ↓
生成部署包并上传
    ↓
服务器备份数据和当前版本
    ↓
构建新镜像
    ↓
执行必要的数据迁移
    ↓
健康检查
    ↓
成功切换，失败回滚
```

这里的关键不是命令有多复杂，而是每一步都有明确的目的：

- 上传前先在本地验证，减少把明显问题带到服务器；
- 更新前保留当前版本和数据备份，确保可以回退；
- 构建完成后再做健康检查，不要只看容器是否处于运行状态；
- 只有新版本真正可用，才认为部署成功。

一个成熟的部署脚本，通常还应该支持只检查、不更新，以及只备份、不切换版本。这些模式在排查问题或执行例行维护时很有价值。

## 出问题时，排查顺序比盲目重启更重要

遇到服务异常时，可以按下面的顺序检查：

1. 查看 Compose 服务是否都处于预期状态；
2. 查看后端服务最近的日志；
3. 确认持久化目录是否正确挂载；
4. 请求健康检查接口，确认服务是否真的能响应；
5. 对照外部平台状态和本地业务账本；
6. 最后再考虑重启、重新构建或回滚。

容器显示“运行中”，并不代表应用一定正常。进程可能还活着，但接口已经无法响应，或者业务循环已经停止。因此，容器状态、应用日志和健康检查应该结合起来看。

如果系统涉及外部账户或交易，排查时还要额外确认外部平台上的真实状态。Docker 只负责运行应用，不能替代对外部账户的核对。

## 安全方面需要注意什么

Docker Compose 配置中可能包含环境变量、服务连接信息、密钥引用方式，甚至会在展开配置时暴露敏感内容。因此，排查问题时不要把完整配置文件直接发到公开场合。

更安全的做法是：

- 只提供与问题相关的配置片段；
- 对密钥、令牌、服务器地址和账号信息进行脱敏；
- 日志中出现敏感信息时先清理再分享；
- 任何会展开变量的命令，都先确认输出范围；
- 生产环境与开发环境使用不同的凭据。

## 写在最后

Docker 的价值并不只是“把程序装进容器”，而是把应用运行所需要的环境、服务关系和部署流程变得更清晰、更可重复。

真正使用 Docker 时，最值得建立的习惯有三个：知道数据放在哪里，知道服务如何更新，知道出现问题时如何回滚。只要这三件事能够说清楚，容器本身就不再神秘，部署也会从一次次手工操作，逐渐变成一套可靠的工程流程。
